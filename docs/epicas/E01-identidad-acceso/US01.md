# US01 — Acceso del gerente / asesor

**Épica:** [E01 — Identidad, acceso y permisos](README.md) · **Issue:** [#16](https://github.com/iokort/Follow-Motors/issues/16) · **Prioridad:** Alta

**Historia:** Como gerente que también ejerce como asesor, quiero entrar al panel operativo con una cuenta habilitada, para gestionar expedientes y citas sin acceso público.

**Dependencias:** US21. **Estado:** backend de autenticación y autorización de GERENTE implementado con MySQL V3; enlace de Angular y validación final pendientes.

## Criterios de aceptación
- [ ] Con credenciales válidas, entra solo a las acciones de gerencia (API protegida; conexión con Angular pendiente).
- [x] Una contraseña incorrecta o una cuenta inactiva no da acceso (pruebas MySQL V3 en CI).
- [x] La autorización se comprueba desde C#, no por ocultar botones (`GET /api/v1/auth/gerencia/acceso` protegido por rol GERENTE).

### Capacitación técnica del equipo SSC

**Motivo del pseudocódigo en los comentarios:** facilitar que los cuatro integrantes del equipo comprendan, expliquen, mantengan y revisen el inicio de sesión. Por tratarse de la primera historia del backend, se añadió una explicación didáctica casi línea por línea directamente en los archivos C#, siguiendo el estilo trabajado en Estructura de Datos: `INICIO`, `Datos`, `Comparar SI`, `SI:SÍ`, `MIENTRAS`, `FIN`. La documentación no altera la ejecución ni introduce cuentas de prueba en el producto.

**Lectura recomendada para capacitación:** primero [`StaffAuthService.cs`](../../../backend/FollowMotors.Api/Application/Auth/StaffAuthService.cs) (datos → validación → MySQL → roles), después [`AuthController.cs`](../../../backend/FollowMotors.Api/Controllers/AuthController.cs) (petición → sesión → respuesta), [`Program.cs`](../../../backend/FollowMotors.Api/Program.cs) (configuración y políticas) y [`MySqlConnectionFactory.cs`](../../../backend/FollowMotors.Api/Infrastructure/MySqlConnectionFactory.cs) (conexión).

**US01 implementa el acceso previsto para producción, no una cuenta simulada.**
El backend usa `usuarios`, `usuarios_roles`, `roles` y `roles_permisos` de la base MySQL V3 existente. Los hash se validan con `PasswordHasher<T>` (ASP.NET Core Identity), sin guardar ni devolver contraseñas. Las cuentas son dadas de alta por el personal autorizado; el portal no ofrece autorregistro.

**Las doce CRC describen responsabilidades y colaboradores, no doce clases obligatorias.** En la implementación varias responsabilidades conviven en los mismos archivos y se separan solo donde SOLID aporta claridad.

### Contrato de uso real

- `POST /api/v1/auth/staff-login` con `{"correo":"...","contrasena":"..."}` valida el usuario existente y emite una cookie `HttpOnly`.
- `GET /api/v1/auth/me` devuelve nombre, roles y permisos de la sesión.
- `GET /api/v1/auth/gerencia/acceso` responde **200** al rol GERENTE, **403** a otro rol autenticado y **401** sin sesión.
- `POST /api/v1/auth/logout` cierra la sesión.
- La configuración de conexión procede de `ConnectionStrings__Default`; no hay contraseñas del sistema en Git.
- La cookie expira en seis horas; la pantalla Angular y su consumo HTTP permanecen pendientes.

**Evidencia:** [`IntegrationSpecs.cs`](../../../backend/FollowMotors.Api.Specs/IntegrationSpecs.cs) prueba con MySQL 8.4 real en un entorno efímero de CI, usuario GERENTE, usuario ASESOR, contraseña errónea, usuario inexistente, cuenta inactiva y rol desactivado. [Guía de backend](../../../backend/README.md).

### SOLID explicado para clase

- **S (responsabilidad única):** `AuthController` trata solicitudes y sesiones; `MySqlStaffAuthService` valida credenciales y consulta roles.
- **O y D (extensible e inversión):** el controlador usa `IStaffAuthService`, no accede a MySQL directamente.
- **I (interfaces pequeñas):** `IStaffAuthService` contiene solo el caso de uso de autenticación.
- **L (sustitución):** cualquier implementación del contrato debe devolver una `StaffIdentity` válida o `null` al rechazar. No hacen falta más interfaces para esta entrega.

**Fuera del alcance de US01:** dar de alta cuentas, restablecer contraseñas y construir el panel de administración completo; se gestionan en otras historias o incrementos.
